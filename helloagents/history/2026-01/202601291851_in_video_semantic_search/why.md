# 变更提案: 本视频语义搜索（无 Embedding / BYOK）

## 需求背景
当前版本的“搜索”偏跨视频，且语义检索依赖 `/embeddings`。但在现阶段：
1) 用户对 embedding 的价值与形态不确定；2) 供应商网关存在 embeddings 权限/可用性不稳定（易出现 401）；3) 目标是先把“单个视频内的体验”打磨到可用、可快、可解释。

因此，本阶段先下线“跨视频语义检索 + embedding”，把资源集中在 **“本视频语义搜索”**：用户在正在看的 B 站视频里输入概念/问题，插件返回最相关的时间点与对应片段，一键跳转。

## 产品分析

### 目标用户与场景
- **用户群体:** 看 B 站长视频/网课/访谈的学习者、工程师、面试准备者
- **使用场景:** 边看边学，想快速定位“讲到某个概念/例子/结论”的位置；看完想回查“某句话/某段推导”
- **核心痛点:** 仅靠手动拖进度条或关键词搜索经常不命中；想问一个“语义问题”（不是原句）也能找到对应片段

### 价值主张与成功指标
- **价值主张:** 不需要 embedding/后端，也能在单视频内提供“像问答一样”的定位能力
- **成功指标:**
  - 单次搜索在常见网络环境下可在 ~2–5s 内出结果（以轻量模型为优先）
  - Top 3 命中率主观可用（用户点击后“确实在讲这个”）
  - 失败时自动回退到“本视频关键词搜索”，用户不会卡死

### 人文关怀
- 默认 BYOK：Key 只存本地；不引导用户上传到后端
- 搜索提示与错误信息避免泄露用户 Key、页面敏感内容

## 变更内容
1. 将现有 UI 的“跨视频搜索”调整为 **本视频搜索**（默认语义搜索，失败回退关键词）
2. 在后台新增“本视频语义搜索”实现：基于字幕分段 + 两阶段检索（关键词召回 → LLM 语义重排）
3. 暂时下线 embedding：不再生成/写入 embeddings，不再展示 embedding 配置项（保留未来恢复的扩展点）

## 影响范围
- **模块:** `src/content-script/*`、`src/background/*`、`src/options/*`、`src/shared/*`
- **文件:** 预计新增/修改消息类型与搜索逻辑；UI 文案更新；（可选）DB 中 embeddings 表保留但不再写入
- **API:** 仅使用现有 LLM Provider（OpenAI-compatible / Gemini）的“对话”能力，不调用 `/embeddings`
- **数据:** 不新增数据结构；复用现有 `segments`（字幕分段产物）

## 核心场景

### 需求: 本视频语义搜索
**模块:** content-script overlay + background search
用户在当前视频页内输入语义问题或概念，获得最相关的时间点列表，点击即跳转到当前视频对应位置。

#### 场景: 语义问题定位
用户输入“RSC 序列化到底解决什么问题？”
- 返回 Top 3–5 个时间点（显示片段摘要/一句命中原因）
- 点击结果：当前视频 `seek` 到该时间点并开始播放（不新开页面）

#### 场景: 未配置 Key / 语义搜索失败
用户未配置 Key 或 LLM 调用失败
- 自动回退为“本视频关键词搜索”
- UI 提示“已回退关键词搜索（可在设置页配置 Key 以启用语义搜索）”

#### 场景: SPA 切换视频/分P切换
用户在同一 tab 内切换到其他 BV 或分P
- 插件内部识别到新 `videoId`，搜索与结果自动切换到当前视频

## 风险评估
- **风险:** LLM 重排成本与延迟不可控  
  **缓解:** 两阶段检索（先召回少量候选），设置超时与回退关键词
- **风险:** Prompt 注入（字幕内容/用户 query）导致输出不可信  
  **缓解:** 强制结构化输出（JSON），做健壮解析与兜底；不执行模型输出的指令
- **风险:** UI 期望与“语义搜索”定义不一致  
  **缓解:** 在设置页/搜索框旁明确解释“语义搜索=用模型在本视频摘要里找相关时间点”，并允许用户切换“关键词/语义”

# BilibiliDry 开发历程与踩坑复盘（知识库）

> 目标：把“开发过程、踩坑、怎么解决、为什么这么解决”沉淀为可复用的工程经验，既能指导后续迭代，也能用于面试/路演讲述。

> 说明：本页内容结合了仓库的 git 历史记录与真实报错/反馈（不是“凭空总结”）。

---

## 1. 我们要解决的问题（产品视角）

- 长视频信息密度低，用户需要“可执行的观看策略”（哪里是干货，哪里是注水）。
- 输出必须可信：**要点必须能回到字幕证据**，否则用户会认为“AI 不靠谱”。
- 约束：
  - Chrome 插件（MV3）
  - 仅用 CC/字幕（不做 OCR）
  - BYOK：用户自备 Key，扩展端直连，不自建托管后端
  - 低等待：先可用（热力图/跳过），再补全（校验/搜索/导出）

---

## 2. 里程碑（工程视角）

1) **MV3 骨架 + Vite/crxjs**：跑通 popup/options/content-script/service worker 的基本链路。  
2) **字幕获取**：从页面/后台拿到 `bvid/aid/cid`，拉取字幕 JSON，得到带时间戳的 `CaptionLine[]`。  
3) **增量分析（边看边出）**：字幕按时间分块，逐块产出 `segments`，热力图逐步更新。  
4) **交互闭环**：一键跳过注水、导出 Markdown、仪表盘查看。  
5) **本视频搜索**：语义重排优先，失败回退关键词（阶段性不依赖 embedding）。  
6) **Reflection Gate**：对关键干货段进行字幕证据对齐校验，弱/不对齐自动降置信度，并可展开查看证据。  
7) **二段式校验 + 自动修正**：小窗严格校验，失败段落进入大窗修复，必要时自动调整时间戳并记录修正来源。  
8) **体验修复**：重新分析不丢旧结果；热力图进度指示符实时更新、支持拖动 seek。

## 3. 关键踩坑与解决方案（含“为什么”）

> 为了让不熟悉工程细节的同学也能看懂，每条都加了“**大白话解释**”：重点解释“**为什么会这样**”和“**怎么修好**”，把专业术语翻译成日常语言。

### 3.1 MV3 + Vite HMR：service worker 拉 `@vite/env` 报 CORS / 注册失败

**现象**：`Service worker registration failed. Status code: 3`，并提示从 `chrome-extension://...` 访问 `http://localhost:3000/@vite/env` 被 CORS 拦截。  

**原因（大白话）**：  
插件后台在开发模式下，需要去你电脑的 `localhost` 拿“热更新用的脚本”。浏览器默认会把这种“扩展 → 本机服务”的访问当成高风险行为，所以如果本机开发服务器没明确说“我允许你这个扩展来访问”，浏览器就直接拦掉。

**原因（工程）**：
- MV3 的 service worker 不是普通网页，开发时经常需要通过 dev server 动态加载脚本。
- dev server 默认不会给 `chrome-extension://*` 返回 `Access-Control-Allow-Origin`。
- 端口变更（3000→3001）时，HMR 客户端/loader 可能仍指向旧端口，导致“明明已跑起来却拉错地址”。

**解决（大白话）**：  
让本机开发服务器“放行”扩展访问（加允许跨域的响应头），并且让“开发服务器端口”和“扩展要去拉的端口”永远保持一致（避免你实际在 3001 跑，它还去 3000 拉）。

**解决（工程）**：
- 为开发加载器增加 CORS 头，允许扩展 origin 拉取 dev 资源。
- 端口选择与对齐：支持自动找空闲端口，并让前端 dev server 与 loader 使用同一端口（含 `PORT_OFFSET`）。
- 文档明确：UI 支持 HMR；service worker 变更通常需要在 `chrome://extensions` 里手动更新/重新加载。

**为什么这么解决（取舍）**：  
这是 MV3 的固有限制。我们不改变生产发布结构（仍是静态 `dist/`），只把开发态做顺滑：开发快、上线稳。

### 3.2 B 站 SPA：同一 tab 切视频/分 P，插件仍显示旧视频信息

**现象**：用户在同一页面跳转到其他 BV/分 P，插件仍显示上一个视频的数据；甚至再次点击分析提示“未解析到视频信息”。  

**原因（大白话）**：  
B 站经常是“页面不刷新、内容直接换掉”。插件如果只在“页面第一次打开”时读取视频信息，那你后面切换视频/分 P，它根本不知道你换了，于是还用旧视频的编号去查数据库、去显示旧结果，就会出现“串台/显示不对”。

**原因（工程）**：
- B 站是 SPA，URL 改了但 content script 不会重载。
- `videoId` 实际是 `bvid+cid`，分 P 的 `cid` 会变化；如果只盯 `bvid` 会串数据。

**解决（大白话）**：  
插件要自己“盯着你有没有换视频”。一旦发现 URL 变了，就把当前状态清掉，重新解析视频信息，并且用更精确的 `bvid+cid` 当作“这条视频的唯一编号”，避免不同分 P 混在一起。

**解决（工程）**：
- 轮询/监听 URL 变化：检测 `window.location.href` 变更后重置状态并重新解析 `__INITIAL_STATE__`。
- 以 `videoId = ${bvid}_${cid}` 作为存储主键，避免串数据。
- 信息解析失败时 fallback 到官方接口补全（页面解析失败 ≠ 无法分析）。

**为什么这么解决（取舍）**：  
比起死盯 DOM（容易随页面改版挂掉），我们更偏向使用“页面状态/官方接口”这类更稳定的来源。

### 3.3 字幕获取：CORS、登录态、need_login_subtitle

**现象**：明明有字幕却提示“没有字幕/解析为空”；或字幕接口返回需要登录。  

**原因（大白话）**：  
“你能在网页上看到字幕”≠“插件能直接下载字幕文件”。有些视频的字幕下载必须带着你的登录状态（Cookie）。如果请求没带 Cookie，服务器就不给字幕，插件就只能判定“没字幕/拿不到”。

**原因（工程）**：
- 某些接口必须带 Cookie（登录态）才能拿到字幕 URL。
- content script 在页面侧 fetch 时容易被 CORS/凭据策略限制。

**解决（大白话）**：  
把“拿字幕”交给后台（service worker）来做：后台更像“扩展自己的后端”，更容易带上登录 Cookie；页面侧拿字幕只当作备用方案（能拿到就用，拿不到也不影响后台兜底）。

**解决（工程）**：
- 后台（service worker）负责“带登录 Cookie”的字幕拉取；页面侧获取作为 best-effort 备用。
- 明确区分“无字幕”与“需要登录才能取字幕”，并在 UI/错误提示中可行动引导。

**补充踩坑（原因/解决的大白话）**：  
字幕文件很多时候是“公开 JSON”，其实不需要 Cookie。反而你带着 Cookie 去请求，会触发更严格的浏览器安全检查，导致 CORS 更容易炸。  
所以拿到字幕 URL 之后，下载字幕 JSON 这一步我们改成“不带 Cookie”，稳定性更高。

**为什么这么解决（取舍）**：  
字幕是整个系统的“原材料”。原材料拿不到，后面干啥都没意义；所以先把字幕链路做稳。

### 3.4 Reflection Gate：证据语言不一致 / 证据被模型改写

**现象**：中文视频里证据变成英文；或证据不是原字幕，而是模型“翻译/改写”的句子。  

**原因（大白话）**：  
模型习惯把东西“讲得更顺、更像人话”，它会自己翻译/改写字幕来当证据。但证据一旦不是原字幕，你回去对照就对不上，用户只会觉得“AI 在编”。

**原因（工程）**：
- LLM 为了“解释性”会改写/翻译证据；这会破坏用户信任与可验证性。

**解决（大白话）**：  
不让模型写“证据内容”，只让它选“第几行字幕最能证明”。证据文本永远由程序从原字幕里截出来展示，这样不可能被翻译/改写。

**解决（工程）**：
- 证据策略改为：模型只返回 `evidenceIndexes`（从我们提供的字幕行里选），UI 永远展示原字幕行文本。

**为什么这么解决（取舍）**：  
证据的目标是“能对得上”。让程序决定展示哪几行原字幕，模型只负责“选编号”，才能彻底杜绝翻译/改写。

### 3.5 “不对齐”的误判：关键句在更后面（例如 3:16 才说到）

**现象**：段落时间窗内确实没讲关键句，但稍后才讲；小窗校验会判 fail。  

**原因（大白话）**：  
我们给模型看的字幕范围太小（比如只给前后 10 秒），关键句如果出现在更后面，它压根看不到，就只能判“不对齐”。另外字幕太密时还会被长度限制截断，等于“把关键句截没了”。

**原因（工程）**：
- 小窗证据窗口太窄，或证据行在长度限制下被截断，模型根本没看到关键句。

**解决（大白话）**：  
先用小窗快速做“严格检查”（快、省钱）；如果判失败，再给它看更大范围的字幕，让它在大范围里重新找证据，并顺便告诉我们“真正对应的时间应该在哪”，我们就能自动把时间戳修正回来。

**解决（工程）**：
- **二段式校验**：
  - `verify`：小窗严格对齐（快速、低成本）
  - `repair`：对 fail 段落使用更大窗证据，重新判定并给出建议时间
- **证据采样**：大窗证据不再“从前往后截断”，改为“超限时均匀抽样覆盖整个窗口”，提升命中概率。
- **自动修正**：当 `repair` 给出建议时间且 verdict 不为 fail 时，自动更新 segment 的时间戳，并记录 `repairedFrom` 便于审计。

**为什么这么解决（取舍）**：  
现实里时间戳就是会飘。我们选择让系统“自己纠错”，产品体验更像“可依赖的工具”，而不是“需要你帮它擦屁股的 demo”。

### 3.6 重新分析覆盖旧结果：用户无法回看上一次

**现象**：点击“重新分析”后，新产出的 Top6 干货与旧的不一致，旧的被覆盖后无法再看。  

**原因（大白话）**：  
重新分析时，新结果是“边算边出来”的。如果 UI 一收到新结果就立刻覆盖旧结果，你会同时经历两件事：  
1) 旧的能用结果突然消失；2) 新的还没算完，显示一直在变。体验就会非常差。

**原因（工程）**：
- 重新分析时我们会不断 push 增量 segments；如果直接写进同一视图，会造成“边算边变”，也会覆盖旧结果。

**解决（大白话）**：  
重新分析期间先“别动旧结果”，继续让你能看能用；新分析彻底结束后再一次性切换到新结果。并且给一个按钮让你能在“上次/本次”之间来回看。

**解决（工程 / MVP 选择）**：
- 重新分析时继续展示当前结果；新分析完成后整体切换。
- 提供“查看上次分析 / 返回本次分析”按钮（当前为内存态）。

**为什么这么解决（取舍）**：  
完整的业界做法是“分析历史版本化”（会更复杂）。为了先把体验救回来，我们先做“不会丢结果”的最小实现。

### 3.7 热力图粉红色指示符：不实时更新 / 不能跟随拖动 / 太粗

**现象**：播放/拖动进度条时粉红指示符不动或反应慢，且视觉太粗影响观感。  

**原因（大白话）**：  
指示符的“位置”来自我们自己存的一个时间值。如果这个时间值更新得不够勤（比如 0.5 秒才更新一次），指示符就会看起来卡顿；如果你拖动进度条时我们没立刻更新这个值，它就不会跟着动。

**原因（工程）**：
- 指示符绑定的是缓存值（ref），更新频率低；拖动 seek 时没有“乐观更新”。
- UI 仅支持 click，不支持 pointer drag。

**解决（大白话）**：  
把“当前播放时间”做成 UI 状态，更新频率更高；你拖动/点击热力图时，先立刻更新 UI（让红线马上动起来），同时再去真正 seek 视频。并且支持按住拖动连续 seek。

**解决（工程）**：
- 用 state 驱动 `currentTime`，提高刷新频率，并在 `seek` 时立即更新 UI（不等 `timeupdate`）。
- 热力图支持按住拖动（pointer events）连续 seek。
- 指示符改为 2px 且居中显示，视觉更接近播放器专业样式。

### 3.8 设置页“空白”：其实是页面没成功渲染（顺手统一了 Key 文案）

**现象**：打开 `chrome-extension://.../options.html` 一片空白，看起来像“插件坏了”。  

**原因（大白话）**：  
设置页就是一个网页。只要它的页面脚本没跑起来（例如入口没加载成功、渲染时报错），你看到的就是白屏。

**解决（大白话）**：  
把设置页的入口/渲染链路修好，让它能稳定把 UI 渲染出来；同时把提示文案改成更通用的“API Key”，避免用户以为只能用某一家。

### 3.9 仪表盘打不开：让后台（service worker）来开 tab 更稳定

**现象**：点击“打开仪表盘”后，Chrome 提示该 `chrome-extension://.../dashboard.html#...` 页面无法连接或已移动。  

**原因（大白话）**：  
页面脚本（content script）更像“寄住在网页里的客人”，权限没那么大。有些时候它想直接打开扩展页面，会被浏览器当成“可疑弹窗/跨域打开”而拦住，所以你会看到打不开。

**解决（大白话）**：  
让扩展后台（service worker）来开 tab。后台才是“扩展自己的人”，用官方 API 开页面更稳定，也更符合权限规则。

### 3.10 Embedding 与跨视频语义检索：很容易被“模型/成本/兼容性”拖死

**现象**：跨视频语义搜索需要 embedding，但不同 provider 的模型不一定支持 embedding；就算支持，也会额外花钱、变慢、还要存很多向量数据。  

**原因（大白话）**：  
embedding 相当于要你“额外做一次大工程”：每个片段都要再请求一次模型拿向量、存到本地、还要做相似度搜索。不同 provider 的 embedding 还不一定能用，最后很容易卡在“调模型/调兼容/调成本”上，主功能反而没交付。

**解决（大白话 / 取舍）**：  
先把“本视频内能搜到”做扎实：关键词先把候选找出来，再让 LLM 负责“把最相关的排前面”；LLM 出问题就回退纯关键词。跨视频 embedding 作为后续升级点。

### 3.11 `.env.local` 的 Key：本地方便，但发布要非常小心

**现象**：你在 `.env.local` 填了 `VITE_*` 的 key，发现插件默认就能用，很爽；但如果把构建产物发给别人，Key 可能也跟着出去了。  

**原因（大白话）**：  
Vite 打包时会把 `VITE_*` 变量“直接写进最终的 JS 文件”。所以你把 `dist/` 发给别人，本质上就是把 Key 也一起发出去了（别人解压就能看到）。

**解决（大白话 / 取舍）**：  
`.env.local` 只用于你自己本地开发/自用构建；如果要发布给别人用，一定要用“设置页填写 Key”的方式，并确保发布包里没有你的私钥。

### 3.12 Model Cascade：进度 100% 了却“还要等一会才有结果”

**现象**：分析进度条显示 100% 后，UI 一度回到“暂无此视频的分析记录”，过一会才出现最终结果；或者最终结果里的 TopK 摘要和你期待的“strong 精炼”不同步。  

**原因（大白话）**：  
我们把“分析流程”拆成两段：先用 cheap 模型快速产出热力图和分段（你就能马上跳过注水），再用 strong 模型把最重要的 TopK 干货摘要精炼得更准。  
如果 UI 把“进度 100%”理解成“所有事情都完成了”，但后面其实还有 strong 在跑，那用户就会感觉“进度在骗人”。更糟的是，如果 UI 在 100% 那一刻就把旧数据清空、等待新数据写入，就会短暂出现“暂无记录”。

**解决（大白话）**：  
把“用户看到的 100%”和“用户最终会看到的结果”对齐：  
要么进度 100% 之前就把 strong TopK 精炼完成，要么明确把 strong 当成“后处理（不影响主结果）”，并在 UI 里显示“正在补全/精炼”。

**解决（工程）**：
- 让 strong TopK 精炼发生在 `ANALYSIS_DONE` 之前（用户进度到 100% 时，看到的就是精炼后的最终摘要）。
- 重新分析时不清空当前结果：UI 保持展示旧结果，同时显示“正在重新分析…”，新结果完成后再整体切换。

**为什么这么解决（取舍）**：  
你明确偏好“进度与结果严格一致”。因此我们宁可让 100% 稍微晚一点到，也不让用户经历“100% 但结果还没好”的割裂体验。

### 3.13 可解释注水：为什么“解释”不能当“证据”，以及默认跳过为什么要保守

**现象**：同样是 WATER 段，有时模型会给出不同的原因；如果我们“看到 WATER 就自动跳”，用户会担心错过真正有信息的内容。  

**原因（大白话）**：  
“注水原因”其实是模型对片段的**解释/判断**，它不是字幕里原封不动写出来的“事实”。解释是会错的；但证据必须能回到字幕原文，错了也能被用户一眼看出来。

**解决（大白话）**：  
把它分清楚：
1) **证据**（字幕原文）用于“证明干货对齐”；  
2) **解释**（注水原因分类/短文案）只用于“帮助用户控制跳过”，不能拿来证明事实。

**为什么这么解决（取舍）**：  
我们优先“避免错跳”。所以默认只自动跳过更安全的类别：**重复 / 无信息增量 / 广告**；像“寒暄/跑题”这类更主观的，我们让用户自己决定要不要跳。

### 3.14 Model Cascade 的工程化落地：强模型只做 TopK，失败不阻断，并把过程指标可视化

**现象**：强模型很贵也很慢；如果每个 chunk 都用强模型，会让用户等太久，成本也不可控。  

**原因（大白话）**：  
长视频的字幕很长，“每一段都用最强模型仔细读一遍”成本会爆炸。我们需要先用 cheap 模型把“哪里值得看”标出来，再把最值钱的少数片段交给强模型精炼。

**解决（大白话）**：  
- cheap：负责“快速产出热力图/跳过策略”（先可用）。  
- strong：只精炼 TopK 干货摘要，并执行对齐校验（精而准）。  
- strong 失败也不影响主流程：最多是“摘要没变得更好”，但不会导致“整个分析没结果”。

**为什么这么解决（面试表达要点）**：  
这是典型的“成本-体验-可信度”三角平衡：
- 体验：先出可用结果（热力图/跳过），用户不干等。  
- 成本：强模型只用在“最值得的地方”（TopK），可控。  
- 可信：把调用耗时/输入输出体量记录成 run 指标，并在 Dashboard 展示，让用户/面试官看到我们不是“拍脑袋”，而是可观测、可优化的工程系统。

---

## 4. 我们一直坚持的工程原则（可用于对外表达）

- **BYOK + 本地优先**：不自建后端，不上传用户 Key；数据保存在本地（IndexedDB + chrome.storage）。
- **先可用再完美**：先产出“可跳过”的 segments，再补校验/搜索/导出。
- **可解释与可核验**：所有关键要点都必须能回到字幕证据；证据必须原文。
- **失败可降级**：语义能力失败时回退关键词；校验失败时降低置信度但不阻断主流程。
